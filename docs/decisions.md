# Журнал решений

Формат записи: решение · какие были варианты · почему выбрали · чем рискуем.

### ADR-001 · Стек: FastAPI + PostgreSQL + React
- **Варианты:** Python/FastAPI; Node/NestJS; серверный рендеринг (Jinja + HTMX).
- **Почему:** в Python лучшие библиотеки для PDF и изображений, FastAPI сам выдаёт OpenAPI-контракт, из которого
  фронтенд генерирует типы. React + Vite — одно SPA с двумя независимыми интерфейсами (`/` и `/operator`).
- **Риск:** два языка в команде; держим контракт в одном месте (`schemas.py` → `docs/api/openapi.json`).

### ADR-002 · Очередь заданий в PostgreSQL, без Redis
- **Варианты:** Celery/arq + Redis; таблица заданий в Postgres.
- **Почему:** одно хранилище — нет рассинхрона «в очереди одно, в базе другое»; критерии прямо запрещают
  состояние «только в очереди». Задание забирается `SELECT … FOR UPDATE SKIP LOCKED` с арендой; пока идёт разбор,
  аренда продлевается, упавший воркер отдаёт задания обратно (проверено `kill -9`, см. architecture.md).
- **Риск:** Postgres как очередь хуже масштабируется на тысячи заданий в секунду — для агентства с запасом хватает.

### ADR-003 · Вход оператора: Keycloak (OIDC) — требование организаторов
- **Варианты:** Keycloak (OIDC, Authorization Code + PKCE); свой логин/пароль с сессиями в БД.
- **Почему:** требование организаторов; стандартный протокол, роли, готовая форма входа. Бэкенд сам проверяет токен
  на каждом запросе: подпись по JWKS, issuer, срок, клиент, роль `operator` (покрыто тестами).
- **Риск:** лишний сервис на стенде; issuer токена должен совпадать с адресом, по которому открывают стенд.

### ADR-004 · Слой модели: один интерфейс, провайдеры по настройке
- **Варианты:** вызывать SDK провайдера прямо из кода; единый слой `backend/app/llm/`.
- **Почему:** п. 5.3 — все обращения в одном месте, провайдер задаётся `LLM_PROVIDER`. Внешний — Qwen3.8-27B от Сбера
  (OpenAI-совместимый API, читает изображения), локальный — Ollama с vision-моделью; есть GigaChat и отдельный
  OCR-шаг olmOCR (`OCR_PROVIDER`).
- **Риск:** у разных моделей разное качество и форма JSON — поэтому терпимый разбор ответа и серверная валидация полей.

### ADR-005 · Двухшаговый разбор: вид документа → поля; минимум полей по документу целиком
- **Варианты:** один общий запрос «найди все поля»; два шага.
- **Почему:** сначала модель определяет вид и читаемость (честный отказ для размытого фото и «не документа»), затем
  извлекает поля по схеме этого вида. Поля документа собираются из всех его файлов (лицо + оборот патента),
  поэтому обязательные поля проверяются на собранном документе, а не на каждом файле.
- **Риск:** два вызова модели на файл — дольше; компенсируем параллельной обработкой (8 потоков).

### ADR-006 · Только разрешительные лицензии; схема БД без миграций
- **Варианты:** PyMuPDF (AGPL) или pypdfium2 (Apache/BSD); Alembic или `create_all`.
- **Почему:** положение (п. 5.8.4) запрещает «вирусные» лицензии — взяли pypdfium2. Схема создаётся при старте —
  экономит время хакатона.
- **Риск:** без миграций изменение схемы на живых данных невозможно — нужен Alembic (docs/limitations.md).
