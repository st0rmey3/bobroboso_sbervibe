## Перед демонстрацией

1. На ПК стенда выполнить `git pull --rebase`, проверить `docker compose ps` и открыть
   `http://localhost:3000`, `http://localhost:3000/operator`. Вход: `operator`, пароль из `OPERATOR_PASSWORD`.
2. Владелец стенда проверяет модель и заполненную `.env`; секреты в терминале и на экране не показываем.
3. Открыть две вкладки: соискатель и оператор. Для показа закрытости подготовить отдельное приватное окно без входа.
4. Подготовить перечисленные ниже файлы в локальной папке `demo-inputs/`. Это условные имена для показа:
   файлы нужно выбрать из набора организаторов или снять перед защитой. В репозитории этой папки нет.
5. Подготовить резервный комплект модели, реальные замеры из `docs/local-model.md` и короткие логи worker.
   При неудаче называем фактический статус и причину; не подменяем разбор заготовленными ответами.

Для ВУ и паспортов Беларуси/Индии на странице соискателя выбрать файлы в «Другой документ — определим сами»,

оставшиеся непринятые файлы. Если все файлы отклонены, подтверждения «Комплект принят» не будет.
В истории карточки событие `file_viewed` подписано «Открыт оригинал»; backend ограничивает частоту записи
одним событием на документ и оператора за десять минут.

Для всех восьми видов открытого набора использовать настоящие файлы из таблицы выше и дополнительно сверить
карточки оператора. Скрипт `python backend/scripts/acceptance_run.py case_docs` помогает наблюдать стадии,
но не измеряет точность полей: его таблица видов не заменяет сравнение с изображениями и эталонной разметкой.

## Переключение модели

Сначала сохранить текущие значения переменных локально, чтобы вернуть исходный провайдер после показа.
Для Ollama на ПК хоста в `.env`:

```dotenv
LLM_PROVIDER=ollama
OLLAMA_URL=http://host.docker.internal:11434
OLLAMA_MODEL=qwen2.5vl:7b
OCR_PROVIDER=none
```

Выполнить `docker compose up -d backend worker`, загрузить другой файл и дождаться фактического результата.
При Ollama внутри Compose URL другой: `http://ollama:11434` (см. `docs/local-model.md`).
Для отдельного локального OCR-шага: `OCR_PROVIDER=ollama`; `OLLAMA_OCR_MODEL` задаёт отдельную модель,
а пустое значение выбирает `OLLAMA_MODEL`. На слабом GPU допустима меньшая модель, но нужно записать её имя
и реальные замеры. Чтобы вернуться к облаку, восстановить прежние значения `.env` и пересоздать backend/worker.

## Участники и вопросы судей

Имена `codex`, `claude`, `gemini` — роли из `AGENTS.md`; на защите отвечает человек, который делал этот участок.
Коммиты нашей frontend-работы подписаны `4looki`. Фамилии остальных участников нужно назвать по фактической команде.

### Frontend — 4looki / Codex

Файлы: `frontend/src/pages/applicant/ApplicantPage.tsx`, `pages/operator/*`, `api/client.ts`, `auth/*`,
`hooks/useResource.ts`, `statusLabels.ts`, `styles.css`, `tests/*`.

1. **Откуда набор документов для страны?** Из `GET /api/public/countries`; выбор в форме меняет список по этому ответу.
2. **Почему ID в ссылке не раскрывает заявку?** Публичный запрос требует отдельный токен в `X-Application-Token`;
   сервер проверяет его. Токен хранится в localStorage, а не в URL.
3. **Как обновляются статусы?** `useResource` запрашивает заявку с паузой, пока есть стадии обработки;
   AbortController отменяет уходящие запросы. Ответ и причины приходят от backend.
4. **Как оператор получает оригинал и CSV?** Запрос с Bearer-заголовком возвращает blob; временный URL показывает
   или скачивает файл. Проверяются HTTP-ошибка, тип CSV и безопасное имя файла.
5. **Где сохраняются правки и расхождения?** PATCH идёт в документ-источник из `MergedField.document_id`;
   backend валидирует и пишет историю. Блок T-022 показывает серверный `cross_checks`, сам совпадение не вычисляет.

### Backend и архитектура — капитан / Claude

Файлы: `backend/app/api/*`, `models.py`, `schemas.py`, `applications.py`, `crosscheck.py`, `auth.py`,
`jobs/*`, `extraction/*`, `llm/*`, `docker-compose.yml`, `keycloak/*`, `docs/*`.

1. **Почему загрузка не ждёт модель?** Обработчик проверяет и сохраняет файл, создаёт Job и отвечает `202`;
   вызов модели выполняет отдельный worker.
2. **Где хранятся данные?** Заявки, поля, задания и аудит — в Postgres; оригиналы — в томе files.
   Перезапуск сервиса не является сбросом томов.
3. **Что происходит при падении worker?** Job арендуется через БД, аренда продлевается; незавершённая работа
   возвращается в обработку после восстановления/истечения аренды. Для показа нужны фактические логи.
4. **Можно ли обойти вход прямой ссылкой?** `require_operator` проверяет JWT: подпись/JWKS, issuer, client,
   срок и роль operator. Зависимость защищает API оператора, включая файлы и выгрузки.
5. **Откуда поле и насколько ему доверять?** Из содержимого через изолированный провайдер модели;
   сервер нормализует формат и проверяет правила. Низкая confidence и несовпадения требуют проверки человеком.

### Стенд, локальная модель и разметка — владелец ПК / Gemini

Файлы и материалы: `docs/local-model.md`, `docs/llm.md`, локальная `.env` (без публикации), Ollama,
реальные файлы `case_docs/`, эталонная разметка `data/open/` вне Git.

1. **Как поднять стенд с нуля?** По README: заполнить `.env`, поднять Compose, проверить сервисы и вход,
   затем выполнить реальные загрузки. Называть только шаги, пройденные на этом ПК.
2. **Как перейти на локальную модель?** Изменить `LLM_PROVIDER`, `OLLAMA_URL`, `OLLAMA_MODEL`, `OCR_PROVIDER`
   и пересоздать backend/worker. Приложение использует тот же интерфейс провайдера.
3. **Какие требования к GPU и памяти?** Назвать фактическую видеокарту, объём VRAM, модель и версию из инструкции;
   вместимость и скорость подтверждаются замерами, а не только названием модели.
4. **Как доказано качество?** Ручные эталоны сверены с документами; `eval_extraction.py` считает метрики.
   Восемь распознанных названий типов не означают, что все значения полей верны.
5. **Что меняется при локальном варианте?** Файлы остаются в локальном контуре, пропадает зависимость от облака;
   скорость и точность могут измениться. Сравнение показываем по реальным цифрам, пропуски не придумываем.

## Что фиксировать после репетиции T-020

В Thread T-020 записать для каждой правки: фактическое имя участника, коммит, проверяемый документ,
результат API/интерфейса и место доказательства. Тестовые токены Playwright подтверждают работу интерфейса,
но не доказывают вход в настоящий Keycloak, работу модели или сохранность после рестарта.
Локальные снимки с полями документов не добавлять в публичный Git. Для публичных материалов использовать
обезличенные изображения; оригиналы и подробный журнал хранить на стенде.
